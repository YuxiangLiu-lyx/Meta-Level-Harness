# Limitations and deviations

POST-HOC notes, 2026-11-11. E0-E5 scores, policies, snapshots, and a1/a2 remain unchanged.

- **One construction repeat.** Each automatic method produced one final harness. Twenty validation scenarios give 20 paired observations, not 80 independent samples. The bootstrap conditions on the current Meta/Refine harnesses and saved outputs; it does not include harness-construction or policy-generation randomness. Its interval crossing zero is not evidence of equivalence.
- **Runtime and model identity.** The experiment used official Codex CLI 0.162.0-alpha.17.2 with the existing ChatGPT subscription, requested model `gpt-6.1-sol`, and medium reasoning effort. The actual serving model and unobservable server context are unknown. This is a Codex-runtime experiment, not a bare-model comparison.
- **Compute comparability.** Meta and Refine each have two logical design stages and the same per-stage settings. Different prompt lengths, completions, caching, and retries prevent a claim of equal actual compute. Meta required three construction attempts; Refine required two.
- **Recovery amendment.** Two attempts had no final response: Meta's final construction stage and Refine's validation position 18 (zero-based task suffix 17). Both received exactly one same-input, fresh-session retry. The initially frozen zero-wrapper-retry rule was amended after the first failure and before validation, under the original bounded-retry authorization. The user's explicit preference confirmation arrived after delivery. This was a disclosed procedural deviation, not a preregistered choice. Completed erroneous outputs were never retried.
- **Timing.** Both attempts had a configured 180-second subprocess timeout. Meta recorded approximately 180 seconds; Refine recorded 1165.7377 wall seconds. The latter discrepancy has no established cause. Wall elapsed time is not inference compute, and strict observed wall-limit enforcement cannot be claimed.
- **Usage.** Both failed attempts lack token usage. Whole-round and affected-method totals remain unknown; known subtotals are labeled separately. Cached input is part of input usage, not an extra additive category. Internal service request counts are unknown.
- **Specification validity.** Passing means satisfying the saved published verification plan. Prose and plans can disagree: the selected development patent scenario describes an assigned-examiner field but its permission sentences do not require assignment, while the plan's ceiling does. No score was changed after this observation. See the package's original patent `intent.md`, `verification_plan.py`, and reference policies. Role/exception ambiguities also limit informal semantic claims.
- **Manual provenance.** Use “fixed baseline prepared in an AI-assisted research-engineering workflow,” retaining Manual only as the historical method label. No independent human-only authorship record exists. Zero experimental design calls does not mean zero AI involvement in setup. The baseline bytes match both E2 and E4 frozen snapshots; see [provenance](manual_provenance.md).
- **Earlier prose correction.** a1 incorrectly described empty semantic-check lists after schema failure as passing. a2 corrected the wording only. Predictions, scores, and denominators did not change; a1/a2 remain preserved.
- **New historical evidence gap.** The expanded P1 audit found 61 unavailable original solver-log hashes across nine earlier outputs in seven shared cache directories. The saved verifier used the same directory for identical scenario/policy/verifier/material keys and rewrote logs for later evaluations. Available logs agree with all 80 saved E4 decisions, but cannot substitute for missing original bytes. All four discordant cases retain their original check hashes. Full historical evidence audit is **INCOMPLETE**. The old audit checked model-event hashes, not solver-log hashes; its earlier clean result was narrower than a full evidence audit.
- **Checksum scope and anonymity.** Per-check and model-file hashes were recorded during execution; validator-gate log hashes were first captured at export. Hashes establish consistency, not independent server attestation or re-executed proofs. The portable package retains original local paths/session IDs as inert provenance and is not an anonymous submission supplement.

Future work, in priority order: independently repeat harness construction; expand validation with a new grouped split and frozen analysis; run a controlled diagnostic with identical target-language/operator guidance across methods; evaluate held-out only after the final method freeze. Before those runs, fix verifier log naming to include attempt identity and verify timing behavior. None of these experiments was started here.
